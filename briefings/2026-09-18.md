## Three ideas

### 1. Recourse
**Pitch:** Insurance and instant claims for financial damage caused by autonomous business-operating AI agents.

**The problem:** Naïve, Runable, and their peers are shipping agents that autonomously pay vendors, sign contracts, and issue refunds. The SMBs adopting them are one bad autonomous decision (a double payment, a wrong wire, a breached SaaS contract) away from a five-figure loss — and there's no insurance product priced for "agent-caused loss," and no accepted way to even adjudicate whose fault it was.

**Why now:** Provenance/audit-log tooling for AI actions (the same category behind this week's HN interest in commit audit trails) has just matured enough to produce a cryptographically verifiable action log — which is exactly the actuarial substrate an insurer needs. Regulatory pressure (EU AI Act enforcement ramping through 2026) is also pushing liability questions to the front.

**Mechanism:** Recourse plugs into agent-orchestration platforms via webhook, logging every consequential action (money movement, contract signature, irreversible API call) to a signed ledger. It prices per-action micro-insurance in real time — a "protect this action" checkbox — and pays claims algorithmically by replaying the logged action against a rules engine instead of a human adjuster.

**First wedge:** Go B2B2B into the agent-ops platforms themselves (Naïve, Runable, and similar) — white-label it as "Agent Assurance," a trust feature they can offer skeptical SMB buyers. Reach them directly; they need exactly this kind of hook to close deals.

**What kills it:** The orchestration platforms build this in-house as a moat feature instead of buying it. Or: agents turn out to be more conservative than the pitch assumes, and the actual loss rate is too thin to underwrite profitably.

**Weirder variant:** Same model, applied to physical AI — insurance for a warehouse humanoid's autonomous decisions, underwritten off the robot's own audited action log.

### 2. Waypost
**Pitch:** A shared memory layer so any coding agent can pick up exactly where any other agent left off.

**The problem:** Engineering orgs now run dozens of parallel agent sessions a day across many repos. Each session's understanding of "why we did X" or "what we tried and reverted" evaporates when the session ends — so agents re-discover the same things, contradict each other's fixes, and sometimes undo each other's work outright.

**Why now:** Coding agents just crossed into continuous, multi-session territory this year (per this week's HN thread on the context bottleneck, and emerging self-hosted MCP memory tools) — but those are single-developer, single-machine patches. MCP standardization in 2026 makes a pluggable, vendor-agnostic version buildable for the first time.

**Mechanism:** Waypost runs as an MCP server per repo, ingesting every agent session's diff, stated rationale, and rejected approaches, embedding and linking them to specific files and commits. Any new session — same tool or a different vendor's — queries it before starting and gets "three agents already tried this refactor here; here's why it got reverted."

**First wedge:** Ship free as a single self-hosted MCP server for power users running multiple agent tools (Claude Code, Cursor, Copilot) against the same repo — that's where the pain is most acute, because the agents are actively working against each other. Distribute directly into the HN/Reddit threads already complaining about this; convert individual users into team accounts once they bring it to work.

**What kills it:** Every major agent vendor ships "good enough" native cross-session memory bundled into their own tool within the next year, since it's an obvious roadmap item — this is a feature, not a company, unless the cross-vendor angle (memory that works even between competing tools) stays genuinely defensible.

**Weirder variant:** Point it at robot fleets instead of repos — a shared "what other robots on this floor already learned about this shelf/door/spill" memory layer, so a warehouse's fleet stops relearning the same edge case robot by robot.

---

### 3. Standby
**Pitch:** An on-demand human safety net that takes over the instant a deployed robot gets stuck.

**The problem:** The $18.8B+ funding robotics in 2026 is buying robots that are autonomous ~90-95% of the time but still choke on edge cases — a dropped item, an ambiguous door, a person crossing its path. Today the fallback is either the robot freezing (costing money per stalled minute) or an in-house remote-ops team most Series A/B robotics companies can't yet justify building.

**Why now:** Robotics deployment volume just crossed the threshold where startups below the Figure/Tesla scale are shipping real fleets into warehouses and homes — but teleoperation infrastructure and a trained "robot rescue" labor pool haven't caught up. It's the same long-tail-of-exceptions gap Scale AI covered for data labeling in 2019, now for real-time embodied intervention.

**Mechanism:** Standby is a marketplace plus real-time teleoperation client that routes a stuck robot's camera/sensor feed to a pool of trained remote pilots within ~2 seconds. A pilot takes manual control just long enough to clear the exception, hands control back to the robot's autonomy stack, and the intervention gets logged as a labeled training example for the robot maker.

**First wedge:** Sell to the mid-tier robotics startups that raised this year's Series A/B rounds and have fleets deployed but no ops staff — integrate as a drop-in SDK against ROS2 so it's a one-sprint integration, not a rebuild.

**What kills it:** Latency and liability. A bad remote intervention caused by network lag turns this into a safety and insurance nightmare fast (which, notably, feeds straight back into Recourse above). Also: the big embodied-AI players build this in-house rather than hand a third party real-time control of their robots.

**Weirder variant:** Flip it — instead of humans rescuing robots, sell it as remote work. People in lower-cost regions teleoperate robots in high-cost cities as a day job, turning "stuck robot" moments into a distributed gig market for physical presence — a mostly-autonomous barista-bot staffed part-time by a remote pilot during the rush.

## Where I might be wrong

Waypost is the weakest of the three — bundled cross-session memory is a near-certain roadmap item for every major agent vendor within a year, and I haven't verified there's a real coordination gap versus each vendor just shipping decent memory for their own tool. Recourse's core assumption — that autonomous agent-caused financial losses are frequent and large enough to underwrite — is unverified; if agent platforms are actually conservative by design, the loss pool may be too thin for the economics to work, and I'd want real incident data from Naïve/Runable-style platforms before committing. Standby's mechanism depends on sub-2-second latency holding up in the field, which is a real open technical question, not just a business one.
