## The three ideas

### 1. Husk
**Pitch:** Auto-generates and prunes your agent context files from real failure data, not vibes.

**The problem:** Every repo now has a graveyard of CLAUDE.md / .cursorrules / AGENTS.md / copilot-instructions.md files, hand-written once and never revisited, and the ETH Zurich data says they're often actively harmful. The people who feel this acutely are platform/DevEx engineers at mid-size eng orgs (50–500 devs) who got told to "write good context files" and have no way to know if theirs help or hurt.

**Why now:** Coding agents now log every tool call, diff, and retry — that failure telemetry didn't exist at this fidelity a year ago. The ETH Zurich paper gave the industry hard evidence that hand-authored context is a liability, not just a nice-to-have, which is the wedge to sell something that replaces the ritual.

**Mechanism:** Husk sits as a proxy/wrapper around your existing coding agent (Claude Code, Cursor, Copilot), watches every task's outcome (did the diff pass CI, get reverted, get argued with in review), and treats each line of context as a hypothesis. Lines that correlate with failure get cut; lines that correlate with first-try success get promoted — output is a continuously A/B-tested, versioned context object instead of a static file humans keep editing by feel.

**First wedge:** Platform teams at Series B–D startups running Claude Code or Cursor fleet-wide, reached via the same DevEx/internal-tools Slack communities and conference talks where the ETH Zurich paper is already being debated.

**What kills it:** The big agent vendors (Anthropic, Cursor, GitHub) have the deepest telemetry and every incentive to build this natively into their own agent rather than let a third party sit in the loop — Husk's moat is temporary unless it becomes genuinely cross-vendor.

**Weirder variant:** Husk for humans — apply the same empirically-pruned-not-hand-written model to employee onboarding docs, auto-cutting wiki pages that never actually help new hires ship their first PR and promoting the ones that do.

### 2. Switchboard
**Pitch:** A vendor-neutral handoff bus so your Copilot, Cursor, and Claude Code agents share one brain.

**The problem:** The Belitsoft number — 12 agents per enterprise, half working alone — names a real problem: a Copilot PR review, a Cursor refactor, and a custom internal agent's incident-response run all happen in the same codebase with zero shared memory. Engineering managers at orgs that didn't standardize on one vendor (most of them, post-2025 tool sprawl) are the ones eating the duplicated work and lost context.

**Why now:** This week's launches (Coder's Agent Relay, Copilot's HydraFusion, Grove) all prove vendors are racing to own multi-agent orchestration — but each is locking users into *their* fleet. Nobody is building the neutral layer between fleets, and MCP-style tool-calling standards from the last two years finally make a vendor-agnostic event log technically plausible.

**Mechanism:** Switchboard is a shared, append-only task/artifact log (think a blackboard architecture) that any agent can write intents and outputs to via a thin adapter. When Agent A finishes a task, it posts a structured handoff record; Agent B (different vendor, different session) can query "what's already been tried on this file" before starting, instead of re-deriving context from scratch or clobbering another agent's in-flight work.

**First wedge:** Dev agencies and consultancies running client work across multiple client-mandated tools (one client requires Copilot, another Cursor) — they feel the duplication most acutely and have the leverage to install a cross-cutting tool since they control the repo, not the client's tool choice.

**What kills it:** No agent vendor benefits from making it easy for their users to hand off to a competitor's agent — Switchboard needs either enough independent leverage to force interoperability (unlikely) or to get acquired/blocked the moment it works.

**Weirder variant:** Same blackboard model, pointed at personal-life agents instead of coding agents — your calendar agent, email agent, and shopping agent posting to one shared log so they hand off tasks to each other without you being the manual router between them.

### 3. ProofOfMotion
**Pitch:** Third-party crash-testing for humanoid robot skills before OEMs ship them into living rooms.

**The problem:** UBTech's U1 and PrimeBOT's Q1 are shipping to actual consumer homes this month, and Kinetic Blocks just opened a marketplace selling third-party training data for robot skills — but nobody is independently verifying that a "fold laundry" or "unload dishwasher" skill module is safe and reliable before it runs unsupervised near a toddler. The acute pain sits with OEMs and insurers who now have consumer liability exposure but no equivalent of a UL/TÜV mark to point to.

**Why now:** This is the first month home humanoid robots ship at real (13,000+ pre-order) volume, and a training-data marketplace just went live, which means third-party, unvetted skill modules are about to enter homes at scale before any certification norm exists — the regulatory and liability shift is happening in real time, not hypothetically.

**Mechanism:** ProofOfMotion runs a candidate skill module through a large bank of simulated home environments (varied lighting, clutter, pets, kids) to generate a statistical failure-rate certificate, then spot-checks the highest-risk scenarios on physical hardware in-house. OEMs and skill marketplaces pay for a certification mark they can show insurers and put in consumer marketing, similar to how UL testing works for appliances.

**First wedge:** The skill marketplaces themselves (like Kinetic Blocks) rather than OEMs directly — they need a trust signal to get any buyer to install a third-party skill on a robot already in someone's home, and one marketplace partnership gets ProofOfMotion in front of every skill vendor selling through it.

**What kills it:** Certification businesses are relationship-driven and slow to build trust (that's what makes UL valuable), and without a regulatory mandate forcing certification, OEMs may simply self-certify with in-house sim testing rather than pay a third party — this only works if a real incident or an insurer requirement forces the issue.

**Weirder variant:** Point the same statistical-certification model at software coding agents instead of robots — certify that a specific agent+prompt+toolset combination reliably performs a defined high-stakes task (rotating prod DB credentials, deploying to prod) before letting it run unsupervised, same simulate-then-spot-check methodology, just in a terminal instead of a living room.

## Where I might be wrong

**Switchboard is the weakest of the three.** The core assumption — that mid-market teams are actually running multiple *different* coding-agent vendors side by side, rather than standardizing on one — needs verification; the Belitsoft "12 agents" stat may be describing large enterprises running many *instances* of agents from one or two vendors, not genuine cross-vendor sprawl, in which case the interoperability pain is much smaller than it sounds and no neutral third party gets invited in. Husk's risk is timing, not demand: if Anthropic or Cursor ship native context auto-pruning in the next two quarters (plausible, given how fresh the ETH Zurich finding is), the whole category disappears into the incumbents. ProofOfMotion is the most defensible but has the slowest sales cycle of the three — it's a bet that an insurance or regulatory forcing function shows up on a startup's timeline, not a decade out.
